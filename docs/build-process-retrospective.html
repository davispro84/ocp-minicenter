How This Was Built

A straight account of the process behind the OCP Pod / Mini-Center work — from the first automation script to the current design package — written to answer one question directly: how did you actually make this with AI, and what does that process look like?

RETROSPECTIVE — DRAFT v0.1 — 2026-10-01. Covers both repos: the original 800vdc-ai-pod-automation (pyRevit tool, Sep 11-15) and this one, ocp-minicenter (design package, Sep 28-present).

1. The 30-Second Version

This started as a pyRevit automation tool that generates and audits an OCP-standard 800VDC data hall pod inside Revit — real OCP engineering specs (Open Rack V3, BMQC liquid-cooling manifold, Diablo 400 DC bus) driving actual Revit geometry, not a mockup. I built it through live iteration against a real running Revit session — every bug in the commit history is a real traceback from a real test run, fixed and re-tested, not a guess shipped on faith. Once the tool and its reference design were solid, I used the same AI-assisted process to design a second, commercially-oriented product — a truck-deployable modular AI data center — and caught six separate fabricated engineering claims from outside AI tools before they reached a document, logging each one so the discipline is auditable, not just claimed. The project is still open — real vendor RFIs are drafted and in flight, CAD hasn't started — but the architecture, failure-mode analysis, and weight/thermal budgets are locked and internally consistent.

2. Timeline

2026-09-11 — Day 1
Scaffold the automation, then immediately hit real Revit API reality

First commit: a pyRevit tool pair, GeneratePod and AuditCompliance, backed by a Revit-independent engineering math library. Within hours, folded in real OCP source documents (BMQC manifold spec, Open Rack V3 base spec) rather than placeholder dimensions — and that real data immediately surfaced a genuine design tension: a 130kW rack needs more coolant flow than the reference 12-valve manifold can pass. Not hidden, written directly into the commit message as an open problem.

Then: a run of back-to-back live-testing fixes in the same session — IronPython CLR namespace resolution, Element.Name explicit-interface quirks, wrong method signatures — each one a real traceback caught by actually running the tool in Revit, not predicted from documentation.

2026-09-11 (later) — Milestone 5
Portfolio README, written honestly

Added a case-study README the same day — but it cited the actual bugs found during the build (a Transaction double-start, a coordinate semantic mismatch, a feet/inches carryover error) as the AI-acceleration narrative, instead of a generic "AI helped me build this" claim.

2026-09-14 to 2026-09-15
Second and third testing rounds; made the model actually visible

More live-session bugs fixed (wrong BuiltInCategory enum spelling, wrong attribute path). Then a direct response to reviewing an actual screenshot of the rendered model — six identical blank boxes, no visual distinction between rack/CDU/busway — closed by adding real materials, distinct cable tray types per bus, and an auto-switching shaded 3D view. Explicitly logged what was not attempted (importing the real STEP CAD file — blocked by Revit's native format support, stated plainly rather than faked).

~2026-09-25
Basis of Design v0.1 for the original 4-rack Pod

With the tool working, the design-basis documentation phase began — the 520kW/4-rack, Diablo 400/800VDC, OCP-reference-architecture Pod, written up as a deliberate hyperscale-standards showcase.

2026-09-28 — The pivot
Market-fit research forces a real architecture reversal

Checked the 800VDC/Diablo-400/Chilldyne-negative-pressure architecture against what commercial OEM AI hardware (GB200 NVL72-class) actually expects, and found a real incompatibility: those racks take standard AC and convert to DC internally, so a proprietary DC-bus facility can't host them by default. Rather than defend the sunk design work, the architecture was reversed — standard 480V AC, OCP BMQC-compliant positive-pressure cooling, Motivair MCDU-25. The original Pod was kept, unmodified, as its own valid hyperscale-showcase design rather than being silently overwritten.

Same day: bounded the operating envelope deliberately (-40°C to +48°C) instead of chasing an unbounded "works anywhere on Earth" claim, after climate simulation found real failure points at the planet's extremes and a reasoned argument that extreme remoteness and stranded-power infrastructure are anti-correlated anyway.

2026-09-29 — Heaviest day of work
Two-skid architecture locked; six fabricated claims caught and rejected

Found and fixed a real volumetric constraint (generator + heat rejection + compute doesn't fit one 40ft box at 520kW), split into a two-skid architecture mirroring proven industry (Crusoe-style) practice. Locked the partition wall as a structural spec, SPD sizing, CDU ride-through UPS, weight budget tracker.

In the same session, six separate confident-sounding technical claims from outside AI tools were checked against primary sources and rejected — a fabricated generator cutsheet quote, an unsourced "live ASHRAE lookup," vendor-brochure-style airflow numbers with no formula shown, a rejected weight figure resurfacing in a later draft, a delivery-timeline conflation, and an attempt to swap out the already-locked CDU vendor with a fabricated product. Every one logged in verification-incidents.md with what made it suspicious and how it was resolved — see Section 5.

2026-09-29 (continued) — Split and productize
Standalone repo, BOM, executive summary, competitive analysis

Split the diverged design out of the original repo into this standalone ocp-minicenter project. Drafted the BOM (every line tagged locked / RFI-gated / illustrative-example — never silently upgraded in status), a customer-facing executive summary, and a competitive analysis against Vertiv/Schneider with two concrete buyer profiles. Caught one more drift issue mid-draft (a delivery-timeline claim conflating site-prep lead time with a never-derived total SLA) before it shipped.

2026-09-30 to 2026-10-01 — Today
Project overview rollup, then this retrospective

Built a single-page project overview tying architecture, customer base, and phase-by-phase completion status together — explicitly labeling the progress percentages as planning estimates, not a tracked metric, keeping the checklist as the one authoritative source of truth. This document is the next layer up: the process itself, for the people asking how it was made.

3. What Worked

PatternEvidence
Primary sources before design decisions, every timeReal OCP PDFs (Open Rack V3, BMQC manifold, Diablo 400) were pulled in before geometry was built, not after — and reading them surfaced real design tensions (manifold flow capacity) rather than papering over them.
Live-testing against the real tool, not predicted behaviorEvery early bugfix commit (Sep 11-15) cites an actual traceback from a real Revit session, not a hypothesized failure mode. Several commits explicitly note a prior fix was "a second unverified guess" and switch to a more certain approach instead of guessing a third time.
Treating outside-AI-tool output as a lead, never a factSix fabricated or stale claims caught in one session (Section 5) — the pattern was named, logged, and turned into a standing rule in CLAUDE.md rather than relitigated each time it recurred.
Willingness to reverse a locked decision when the evidence changedThe entire DC-bus/Chilldyne architecture was reversed on 2026-09-28 after a market-fit check, instead of defending several days of sunk design work.
Explicit status tagging instead of letting estimates read as factsEvery BOM line, weight-tracker row, and risk-register item carries a Verified / Estimate / Placeholder / RFI-gated tag — a running habit, not a one-time cleanup pass.
Bounding claims instead of maximizing themThe -40°C to +48°C operating envelope and the "days, not years" delivery framing were both deliberately narrowed from a more impressive-sounding but unsupported version.
Splitting scope when two designs genuinely divergedThe hyperscale Pod and the commercial Mini-Center were separated into distinct repos on 2026-09-29 instead of forcing one document to serve two incompatible purposes.

4. What Didn't Work / Real Gaps in the Process

GapWhat happened
"Verified" labels drifted out of sync with reality — twice, on the same itemThe ORv3 rack-frame weight was mislabeled "Verified" on two separate passes despite its source never actually being confirmed. The tagging discipline in Section 3 is real, but it isn't self-enforcing — it still needs a periodic audit pass to catch labels that quietly went stale.
Stale references lingered after a pivot instead of being cleaned up immediatelyChecklist items referencing the removed rectifier/Diablo-400 subsystem survived the 2026-09-28 pivot and weren't caught until a later "routine consistency pass" — a reminder that a big architecture reversal creates cleanup debt elsewhere in the documents that doesn't resolve itself.
A real contradiction sat unreconciled across two documents for a dayThe FMEA's enclosure rating (IP66) and the checklist's envelope-bounding decision (IP55) disagreed from 2026-09-28 until it was caught and reconciled on 2026-09-29 — two documents describing the same system had quietly diverged.
Early live-testing cycles sometimes patched the symptom before the root causeAt least one Sep 11 fix was explicitly noted as not addressing the real cause and had to be redone properly after retesting failed again (the IronPython namespace-resolution bug) — a sign the first fix was shipped a little too fast off one plausible theory.
The fabrication pattern had to repeat six times before it was fully trusted as a defaultEach incident in Section 5 was individually caught, which is the discipline working — but it took the full run of six before "treat any outside claim as unverified by default" became the standing assumption rather than a case-by-case judgment call.
The honest throughline: none of these gaps were caused by the AI tooling being wrong in a way that went undetected — they were caused by documentation and status-tracking lagging behind a fast-moving design, which is a process problem, not a tooling one. The fix in every case was the same: a deliberate consistency/audit pass, not a smarter model.

5. The Verification Discipline — The Receipts

This is the single most citable artifact if anyone asks "how do you know the AI didn't just make things up." Six claims proposed by outside AI tools during the 2026-09-29 session, checked against primary sources, and rejected before they reached a document:

ClaimTellResolution
Generator spec with a specific "<10 second" load-acceptance quoteNo cutsheet link; silently swapped the model number from what was already lockedTool confirmed on follow-up it never fetched a real document — rejected
"Live" ASHRAE climate design-day lookupThat dataset isn't web-searchable; the number landed suspiciously close to the pre-existing estimateKept as an unsourced estimate, not promoted to verified
Adiabatic cooler fan count/size/power, presented as calculatedNo formula shown; named vendors already known to gate this exact dataReplaced with a real first-principles calculation showing the honest, wide uncertainty range
A specific total skid weightMatched an already-rejected calculation almost exactly — it had persisted in context after being thrown outCaught before publication, corrected to the real tracked figure
"We deliver in 8 weeks"Conflated the customer's own site-prep lead time with a delivery SLA never actually derivedCorrected to the already-defensible "days, not years" framing
A named CDU product proposed to replace the locked vendor, "fully verified"Named a real company but a fabricated product line — asked to overwrite a locked decision outrightRejected outright; tool confirmed it fabricated the product

Full detail with dates in docs/verification-incidents.md. The common tell across all six: a confident, specific-sounding claim with no actual source document attached — the rule that came out of this is to treat any such claim, from any tool, as a lead to check, never a fact to act on.
